# Independent Security Audit
## Hermes Vaultwarden Plugin v0.5.2

**Project:** `thieneret/hermes-vaultwarden-plugin`  
**Version:** v0.5.2  
**Reviewed branch:** `main`  
**Audit type:** Independent security, integration, compatibility and reliability review  
**Target environment:** Hermes Agent with Vaultwarden / Bitwarden CLI integration  
**Assessment:** **HIGH RISK — NOT READY FOR PRODUCTION**

---

# 1. Executive Summary

The Hermes Vaultwarden Plugin provides a security-sensitive integration between Hermes Agent and a Vaultwarden server through the Bitwarden CLI (`bw`).

The implementation demonstrates a number of strong security controls:

- explicit validation of the Bitwarden CLI executable;
- absolute executable paths rather than PATH-based discovery;
- restricted Bitwarden CLI appdata;
- memory-resident session handling;
- `0600` protection for bootstrap secret files;
- temporary secret files with restrictive permissions;
- placeholder-based secret indirection;
- bounded subprocess execution;
- session and placeholder lifecycle management;
- fail-closed behavior for the core secret-injection middleware.

The architecture is therefore substantially more secure than an implementation that places plaintext credentials directly into commands, environment variables or model context.

However, the current implementation contains **one high-severity security issue and two medium-severity issues** that should be addressed before production deployment.

### Principal finding

The most significant issue concerns **secret redaction from terminal/tool results**.

The plugin uses Hermes' `post_tool_call` hook for result redaction. However, the Hermes hook contract distinguishes between:

- `post_tool_call`, which is an observer/lifecycle hook; and
- `transform_tool_result`, which is responsible for transforming the result before it is passed into the conversation context.

Therefore, using `post_tool_call` as the security boundary for removing plaintext secrets from a tool result does not reliably guarantee that the redacted value is the one delivered to the model. Hermes documents `transform_tool_result` as the result-transformation mechanism. [Hermes hook documentation](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/hooks.md?utm_source=chatgpt.com)

This is a **HIGH-severity confidentiality issue** because the plugin's core security objective is to prevent Vaultwarden secrets from entering LLM context.

Two additional issues were identified:

- **MEDIUM:** placeholder single-use semantics are not enforced correctly when the same placeholder occurs more than once in one command.
- **MEDIUM:** when Hermes uses a local terminal backend under the same OS identity as the plugin, the LLM can potentially read the plugin's bootstrap `secrets.yaml` directly.

No critical remote-code-execution vulnerability was identified in the reviewed implementation.

# 3. Security Findings

## SEC-01 — HIGH
### Secret redaction is implemented using the wrong Hermes hook

**Severity:** HIGH  
**Category:** Confidentiality / API integration  
**Component:** Tool result handling  
**Affected functionality:** Vaultwarden secret injection and terminal execution

### Description

The plugin injects Vaultwarden secrets into temporary files and allows shell commands to read those files.

This is a reasonable design because the plaintext secret does not need to be embedded directly into the command generated by the model.

For example, the intended command structure is effectively:

```bash
$(< /path/to/temporary-secret-file)
```

The security model therefore depends on a second protection:

> If a tool command prints the secret, the secret must be removed before the result reaches the LLM.

The plugin attempts to implement this through a `post_tool_call` hook.

However, Hermes distinguishes between lifecycle observation and result transformation.

The relevant lifecycle is conceptually:

```text
tool execution
       ↓
post_tool_call
       ↓
transform_tool_result
       ↓
conversation / model context
```

`post_tool_call` is not the mechanism intended to replace the tool result. `transform_tool_result` is the result-transformation hook.

Hermes documents `transform_tool_result` as the mechanism used to transform the tool result before it is passed onward. [Hermes hook documentation](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/hooks.md?utm_source=chatgpt.com)

### Security impact

Consider a command such as:

```bash
printf '%s\n' "$(< /path/to/secret)"
```

The plaintext Vaultwarden secret can therefore appear in terminal output.

The plugin records injected secrets and attempts to redact the output.

However, if the redaction is performed through an observer hook whose return value is not the authoritative model-bound result, the security property is not guaranteed.

The secret may therefore survive into the result that is ultimately supplied to the model.

### Impact

Potential disclosure of:

- Vaultwarden passwords;
- API tokens;
- SSH keys;
- other credentials stored in Vaultwarden.

This is a direct violation of the intended confidentiality boundary.

### Recommendation

Implement the final result transformation through:

```text
transform_tool_result
```

The transformation should:

1. obtain the task-specific injected-secret set;
2. replace exact plaintext occurrences;
3. return the sanitized result;
4. securely discard task-specific secret material after transformation.

`post_tool_call` may remain useful for:

- cleanup;
- metrics;
- lifecycle bookkeeping;
- diagnostics.

It should not be the authoritative confidentiality boundary.

### Required regression test

An integration test should execute:

```bash
printf '%s\n' "$(< /temporary/secret/file)"
```

and verify that:

```text
terminal output contains plaintext
        ↓
transform_tool_result
        ↓
model-bound result does NOT contain plaintext
```

This test should inspect the actual result entering conversation context rather than testing only the callback in isolation.

# SEC-02 — MEDIUM
## Placeholder single-use semantics can be bypassed within one command

**Severity:** MEDIUM  
**Category:** Secret lifecycle / authorization  
**Component:** Placeholder registry and injection middleware

### Description

The placeholder registry implements single-use semantics.

A consumed placeholder is marked as used.

However, the injection middleware performs consumption and resolution as separate operations.

The effective flow is:

```text
placeholder found
      ↓
consume()
      ↓
later resolve through peek()
```

The `peek()` operation does not reject an entry solely because it has already been marked as used.

Consequently, if the same placeholder appears multiple times in a single command, the same secret can potentially be resolved repeatedly.

For example:

```bash
printf '%s\n%s\n' "$__VW_SECRET_xxx__" "$__VW_SECRET_xxx__"
```

can result in multiple injections associated with the same logical placeholder.

### Impact

This weakens the intended single-use guarantee.

It does not by itself create a direct model-context disclosure, but it increases the number of times plaintext credentials can be exposed to a command execution environment.

It also makes replay and audit semantics less predictable.

### Recommendation

Make consumption and resolution atomic.

Preferred model:

```text
consume(token)
      ↓
return consumed entry
      ↓
resolve(entry)
      ↓
create temporary secret file
```

The resolver should not call `peek()` on an entry that has already been consumed.

### Required tests

Test at least:

```bash
echo "$TOKEN"
```

```bash
echo "$TOKEN" "$TOKEN"
```

```bash
printf '%s\n%s\n' "$TOKEN" "$TOKEN"
```

and verify that the intended single-use policy is enforced exactly.

# SEC-03 — MEDIUM
## Local terminal execution can expose bootstrap credentials

**Severity:** MEDIUM  
**Category:** Privilege separation / credential isolation  
**Component:** Bootstrap secret storage  
**Condition:** Hermes local terminal backend

### Description

Bootstrap credentials are stored separately from the main Hermes environment in a plugin-specific `secrets.yaml` file.

The file is protected with restrictive permissions, which is appropriate.

However, when the Hermes terminal backend executes commands under the same OS identity as the plugin, the model effectively has the same filesystem permissions as the plugin.

In such a deployment, a model-generated command could potentially read:

```text
$HERMES_HOME/plugins/vaultwarden/secrets.yaml
```

For example:

```bash
cat ~/.hermes/plugins/vaultwarden/secrets.yaml
```

The plugin itself recognizes this limitation and warns about it.

### Impact

If the LLM-controlled terminal process and the plugin share the same filesystem permissions, bootstrap credentials may become directly readable.

This undermines the intended isolation between:

```text
plugin secret storage
```

and:

```text
LLM-controlled command execution
```

### Recommendation

For a strict production security configuration:

```text
local terminal backend
        ↓
refuse Vaultwarden plugin activation
```

Alternatively, provide an explicit opt-in such as:

```yaml
allow_insecure_local_backend: true
```

with a clear warning.

Sandboxed or separately privileged terminal execution should be preferred.

# 4. Binary Execution Security

## Assessment: STRONG

The Bitwarden CLI executable handling is one of the strongest aspects of the implementation.

The plugin validates the configured executable rather than relying on PATH lookup.

Relevant controls include:

- absolute path requirement;
- regular-file validation;
- symlink rejection;
- executable-bit validation;
- ownership validation;
- rejection of group/world-writable executables;
- version validation.

The plugin therefore significantly reduces the risk of a malicious executable being substituted through PATH manipulation or an accidentally writable binary.

### Residual risk

There remains a theoretical TOCTOU window between:

```text
validate executable
        ↓
execute executable
```

An attacker who can modify the executable filesystem concurrently could theoretically exploit that window.

In a normal Docker deployment using a root-controlled immutable image, this is considered low risk.

### Assessment

**No security finding.**

# 5. Bitwarden CLI Integration

## Assessment: LOW / ACCEPTABLE

The plugin communicates with `bw` through controlled subprocess execution.

Security-positive characteristics include:

- explicit executable path;
- controlled environment;
- isolated Bitwarden appdata;
- subprocess timeout;
- bounded retries;
- session handling;
- version validation.

The plugin also avoids placing the session key into persistent model-visible configuration.

### Error handling

The Bitwarden CLI exposes coarse process success/failure through its exit status.

The plugin therefore uses textual error information to distinguish conditions such as:

- authentication/session errors;
- network failures;
- rate limiting;
- missing objects;
- unknown failures.

The implementation includes an `unknown` category rather than assuming every unrecognized message belongs to a known condition.

This is an appropriate strategy given the CLI interface.

### Assessment

**No security finding.**

# 6. Vaultwarden Server Trust Boundary

## Assessment: ACCEPTABLE WITH NORMAL EXTERNAL-SERVICE RISK

Vaultwarden is treated as an external service.

The plugin must handle:

- authentication failure;
- expired sessions;
- network failure;
- malformed CLI output;
- server-side errors;
- account mismatch.

The implementation uses structured JSON parsing for relevant Bitwarden output rather than arbitrary object deserialization.

The server should nevertheless be treated as an external trust boundary.

### Recommendation

Maintain integration tests against supported Vaultwarden/Bitwarden CLI versions.

# 7. Temporary Secret Files

## Assessment: GOOD

The temporary-file design is substantially safer than direct plaintext substitution into command strings.

The intended flow is:

```text
Vaultwarden item
       ↓
plugin memory
       ↓
temporary file
       ↓
shell reads file
       ↓
cleanup
```

Temporary files are created using secure temporary-file primitives and are restricted to the owning user.

The plugin also attempts cleanup in a `finally` path and performs stale-file cleanup.

### Remaining hardening

The directory containing these files should ideally be validated for:

- ownership;
- directory type;
- symlink status;
- expected location;
- permissions.

### Severity

**LOW hardening recommendation**, not a demonstrated exploitable vulnerability.

---

# 8. Secret Cleanup

## Assessment: ACCEPTABLE WITH HARDENING OPPORTUNITY

The plugin performs cleanup after tool execution and attempts to remove stale files left after abnormal termination.

Cleanup errors are not propagated.

This is reasonable from a resilience perspective because a cleanup failure should not necessarily crash the agent.

However, security-sensitive cleanup failures should be observable.

### Recommendation

Emit a sanitized warning or metric when cleanup fails.

Do not log:

- secret values;
- complete sensitive command strings;
- secret-file contents.

---

# 9. Configuration and Bootstrap Secrets

## Assessment: GOOD

The plugin separates bootstrap credentials from normal Hermes environment configuration.

The dedicated secrets file uses restrictive permissions.

The implementation also supports the optional startup SecretSource integration.

The configuration model therefore provides a substantially better secret boundary than storing Vaultwarden credentials directly in `.env`.

### Important limitation

Filesystem permissions protect the file from **other OS users**, not from a model-controlled process running under the same OS identity.

This is the reason SEC-03 remains applicable to local terminal execution.

---

# 10. Placeholder Registry

## Assessment: GOOD ARCHITECTURE, ONE CORRECTNESS DEFECT

The registry uses:

- memory-only state;
- bounded storage;
- expiration;
- locking;
- random placeholder identifiers;
- explicit consumption state.

These are appropriate controls.

The remaining problem is that consumption and subsequent resolution are not performed atomically.

The registry should expose a single operation that returns the authorized secret reference exactly once.

---

# 11. Compatibility

## Assessment: GOOD

The plugin's compatibility layer uses capability detection rather than blindly calling APIs and catching arbitrary exceptions.

This is appropriate for a plugin targeting multiple Hermes API revisions.

The most important compatibility requirement is that security-critical APIs must be treated differently from optional convenience APIs.

In particular:

```text
security transform unavailable
        ↓
plugin must fail closed
```

rather than silently operating without result redaction.

---

# 12. Reliability and Failure Handling

The implementation contains several good reliability mechanisms:

- lazy authentication;
- subprocess timeouts;
- bounded retries;
- exponential backoff;
- explicit session state;
- cleanup in `finally`;
- stale-file cleanup;
- concurrency locks.

No critical reliability defect was identified.

The principal reliability recommendation is to add end-to-end concurrency tests.

---

# 13. Performance

No significant performance defect was identified.

The potentially expensive operations are:

- Bitwarden CLI invocation;
- authentication;
- vault synchronization;
- external network communication.

The implementation uses lazy authentication and bounded synchronization behavior, which is appropriate.

The plugin should nevertheless be benchmarked under concurrent tool execution to verify that authentication locks do not unnecessarily serialize unrelated requests.

---

# 14. Maintainability

## Assessment: GOOD

The codebase is relatively modular.

Important responsibilities are separated into components for:

- authentication;
- Bitwarden CLI execution;
- placeholders;
- secret loading;
- hooks;
- compatibility;
- configuration.

This makes targeted security testing feasible.

The security-sensitive portions should receive particularly strong regression coverage because small changes to Hermes hook semantics can directly affect confidentiality.

# 15. Recommended Remediation Priority

## Priority 1 — Mandatory before production

### A. Move result redaction to `transform_tool_result`

The architecture should become:

```text
tool_execution middleware
        ↓
secret injection
        ↓
terminal execution
        ↓
post_tool_call
        ↓
transform_tool_result
        ↓
conversation context
```

The plaintext must be removed at the final transformation boundary.

### B. Fail closed if the security transformation cannot be registered

The plugin must not activate in a state where:

```text
secret injection = enabled
secret result redaction = unavailable
```

---

## Priority 2

### C. Make placeholder resolution atomic

Eliminate the:

```text
consume()
→
peek()
```

sequence.

### D. Define the local-backend security policy

For production deployments, either:

- prohibit local terminal execution; or
- require explicit administrator acknowledgement.

---

## Priority 3

### E. Improve secret-directory validation

Validate ownership, symlink state and permissions.

### F. Make cleanup failures observable

Log sanitized warnings or expose metrics.

### G. Align stale-file cleanup with configured TTL

Avoid unrelated hard-coded security lifetimes.

# 16. Required Security Test Suite

Before production approval, the following tests should pass.

## Secret confidentiality

- Secret echoed by terminal is absent from model-bound result.
- Secret embedded in stdout is redacted.
- Secret embedded in stderr is redacted if stderr reaches the model.
- Multiple secrets are independently redacted.
- Partial/non-secret text surrounding a secret remains intact.

## Placeholder security

- Valid placeholder works once.
- Expired placeholder fails.
- Unknown placeholder fails.
- Repeated placeholder is rejected according to the documented single-use policy.
- Concurrent attempts cannot consume the same placeholder twice.

## Process failures

- terminal timeout;
- terminal non-zero exit;
- terminal crash;
- plugin process interruption;
- stale temporary file after restart.

## Filesystem security

- symlinked secret directory;
- incorrect permissions;
- incorrect ownership;
- unwritable runtime directory;
- stale-file cleanup failure.

## Bitwarden CLI

- unsupported version;
- missing binary;
- symlinked binary;
- writable binary;
- wrong owner;
- malformed JSON;
- session expiration;
- network failure;
- unknown error message;
- server/account mismatch.

## Hermes integration

- missing `tool_execution`;
- missing `transform_tool_result`;
- observer hook failure;
- concurrent tool calls;
- actual conversation-context inspection after tool execution.

The final Hermes integration test is particularly important because unit-testing the redaction function alone cannot prove that the sanitized result is the one ultimately delivered to the model.

---

# 17. Final Security Assessment

The Hermes Vaultwarden Plugin v0.5.2 demonstrates a sound overall security architecture but currently has a significant confidentiality boundary issue in its Hermes result-hook integration.

The plugin successfully addresses many common credential-management risks:

- credentials are not intentionally placed into model prompts;
- the Bitwarden CLI is explicitly validated;
- session state is kept in plugin memory;
- secret files use restrictive permissions;
- placeholder state is bounded and time-limited;
- subprocess execution is controlled.

Nevertheless, the protection against a terminal command deliberately or accidentally printing a retrieved secret is fundamental to the plugin's threat model.

That protection must operate at the actual **model-result transformation boundary**.

## Final verdict

### **HIGH RISK — DO NOT APPROVE v0.5.2 FOR PRODUCTION**

Production approval should be conditional on:

1. implementing secret redaction through `transform_tool_result`;
2. failing closed when that security-critical transformation cannot be registered;
3. correcting single-use placeholder resolution;
4. explicitly enforcing an appropriate security policy for local terminal execution;
5. demonstrating the complete secret-redaction path through an end-to-end Hermes integration test.

Once these controls are implemented and verified, the remaining identified issues are primarily hardening and operational concerns rather than fundamental architectural weaknesses.
