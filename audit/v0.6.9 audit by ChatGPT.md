# Hermes Vaultwarden Plugin v0.6.9
## Independent Security Audit Report

**Audit target:** `hermes-vaultwarden-plugin` v0.6.9  
**Host:** Hermes Agent 2026.10.x  
**Runtime:** Python 3.10+  
**Platform:** Linux  
**Deployment model:** Deployment-agnostic  
**Third-party components:** Bitwarden CLI (`bw`) and Vaultwarden  
**Audit focus:** Security, secret handling, subprocess integration, lifecycle hooks, filesystem security, compatibility, reliability, privacy, and code quality

---

## 1. Executive Summary

The `hermes-vaultwarden-plugin` v0.6.9 implements a comparatively strong security model for integrating Vaultwarden/Bitwarden CLI functionality into Hermes Agent.

The most important security properties are centered around:

- keeping retrieved secrets out of the LLM context;
- opaque placeholder-based secret handling;
- authoritative tool-result redaction;
- atomic placeholder resolution;
- isolated subprocess environments;
- memory-only handling of `BW_SESSION`;
- hardened filesystem locations for temporary secret material;
- restrictive permissions on bootstrap and secret files;
- fail-closed initialization and lifecycle handling;
- scoped and thread-safe redaction;
- prevention of direct shell interpretation of secret values.

The implementation nevertheless contains several areas requiring remediation or hardening.

### Overall risk: **MEDIUM**

The principal concerns identified are:

1. **HVA-01 — SSH secret/redaction lifecycle management**  
   Secret registrations associated with SSH operations may not always have a corresponding lifecycle release, potentially causing plaintext secrets to remain in the process-wide redaction registry longer than necessary.

2. **HVA-02 — `server_url` handling and sensitive URL components**  
   The configuration validation permits URL structures containing user-information, query parameters, or fragments. If such a URL reaches logging or diagnostic output, sensitive material could potentially be exposed.

3. **HVA-03 — File-based secret input TOCTOU/symlink hardening**  
   `password_file` / `pass_file` handling performs filesystem checks and subsequent file access without providing the strongest possible resistance against symlink substitution or time-of-check/time-of-use races.

4. **HVA-04 — SSH temporary socket cleanup**  
   A cleanup path involving SSH sockets may potentially unlink a filesystem object after an unsuccessful `ssh-add -l` operation. The practical exploitability depends on control over the relevant environment and filesystem path.

5. **HVA-05 — Test-suite completion verification**  
   The available audit execution evidence did not establish complete termination of the entire test suite in the audit environment. This is primarily a verification/reliability limitation rather than a demonstrated security vulnerability.

No security finding is raised concerning the plugin's method for determining the Hermes terminal backend. The terminal backend is a host execution property rather than plugin configuration, and there is no supported plugin-facing Hermes API that exposes this setting. The current approach should instead be **explicitly documented as an intentional compatibility exception**, including its rationale and limitations.

# 3. Detailed Findings

## HVA-01 — SSH Secret / Redaction Lifecycle Management

**Severity:** Medium  
**Category:** Security / Reliability

### Description

The plugin maintains plaintext secrets in its redaction infrastructure so that sensitive values appearing in tool output or subprocess-related data can be removed before reaching the user or LLM context.

The normal lifecycle is scoped and reference-counted. However, some SSH-related execution paths register secrets through `register_secret()` without a guaranteed matching `forget_secret()` operation.

Consequently, a secret may remain registered in the redaction filter after the corresponding SSH operation has completed.

### Security impact

The primary impact is not direct disclosure: retaining a secret in the redaction registry does not itself expose it to the LLM.

The concern is instead that plaintext secret material remains resident in process memory for longer than necessary.

Potential consequences include:

- unnecessary lifetime extension of sensitive data;
- growth of the redaction registry during repeated SSH operations;
- increased exposure in the event of process-memory compromise;
- degraded lifecycle guarantees compared with the otherwise scoped secret-handling design.

### Assessment

**Confirmed design/lifecycle weakness.**

The issue should be addressed by making SSH secret registration follow the same strict ownership and lifetime semantics used elsewhere in the plugin.

### Recommendation

Ensure every SSH-specific secret registration has deterministic lifecycle ownership.

Preferred approaches include:

- wrapping registration and release in a context manager;
- attaching the registration to the existing execution-scoped secret lifecycle;
- using reference-counted acquisition/release consistently;
- ensuring exceptional SSH paths release the secret as well.

A regression test should verify that the redaction registry returns to its expected state after both successful and failed SSH operations.

# 4. HVA-02 — `server_url` Handling and Sensitive URL Components

**Severity:** Medium  
**Category:** Security / Privacy

### Description

The plugin validates the Vaultwarden/Bitwarden server URL and restricts its scheme appropriately.

However, the URL validation does not necessarily prohibit all URL components capable of carrying sensitive information, such as:

- username/password user-information;
- query parameters;
- fragments.

A URL containing credentials or tokens can therefore potentially enter configuration or diagnostic paths in a form that is more sensitive than a normal server origin.

### Security impact

If such a URL is logged, included in diagnostics, error messages, status output, or otherwise exposed, credentials or other sensitive values embedded in the URL could be disclosed.

This is particularly relevant because URL strings are often treated as non-secret configuration data even when they contain credential-bearing components.

### Recommendation

Prefer accepting only the components required to identify the Vaultwarden server.

At minimum:

- reject URL user-information;
- reject fragments;
- reject unnecessary query parameters;
- normalize the accepted URL representation;
- avoid logging the complete configured URL where possible.

If query parameters or other components are intentionally required for compatibility, they should be explicitly documented and sanitized before logging.

# 5. HVA-03 — File-Based Secret Input TOCTOU / Symlink Hardening

**Severity:** Low  
**Category:** Security

### Description

The plugin supports file-based secret inputs such as:

- `password_file`;
- `pass_file`.

These mechanisms are preferable to directly supplying plaintext secrets because they reduce the need to place the secret directly into command arguments or other user-visible structures.

The current validation checks file properties before opening/reading the file. However, ordinary path-based checks can be vulnerable to a time-of-check/time-of-use race or symlink substitution between validation and access.

### Security impact

Under an attacker-controlled filesystem scenario, a checked path could potentially be replaced between validation and subsequent access.

The practical exploitability depends heavily on filesystem ownership and the permissions available to an attacker.

This is therefore primarily a defense-in-depth issue.

### Recommendation

Where practical:

- use `lstat()` before following a path;
- reject symbolic links explicitly;
- verify ownership and permissions;
- open the file using restrictive flags where available;
- validate the opened file descriptor rather than relying exclusively on a prior path check;
- minimize the interval between validation and opening.

The implementation should retain its existing fail-closed behavior for invalid permissions or unexpected file types.

# 6. HVA-04 — SSH Temporary Socket Cleanup

**Severity:** Low  
**Category:** Security / Reliability

### Description

An SSH-related cleanup path can remove a temporary socket/path following an unsuccessful `ssh-add -l` operation.

The concern is that a non-zero exit status does not by itself prove that the expected temporary socket still refers to the exact object originally created by the plugin.

### Security impact

In an environment where an attacker can manipulate the relevant filesystem namespace or influence the temporary socket path, a cleanup operation could potentially remove an unintended filesystem object.

The realistic exploitability is limited by the surrounding filesystem permissions and temporary-path controls.

### Recommendation

Cleanup should be narrowly scoped to resources demonstrably created by the current execution.

Possible improvements include:

- retaining the original file descriptor or creation identity where feasible;
- verifying object type before unlinking;
- using secure temporary-object creation primitives;
- ensuring cleanup paths cannot be redirected through symlinks;
- treating cleanup as best-effort but fail-safe.

Cleanup failures should remain observable through sanitized diagnostics without exposing secret material.

# 7. HVA-05 — Test-Suite Completion Verification

**Severity:** Informational  
**Category:** Verification / Reliability

### Description

The plugin contains an extensive automated test suite covering security-sensitive behavior, including:

- redaction;
- placeholder resolution;
- filesystem hardening;
- secret lifecycle;
- environment isolation;
- concurrency;
- lifecycle hooks;
- shell injection resistance;
- bootstrap secrets;
- status handling;
- fail-closed behavior.

The available execution evidence established successful execution of targeted security-relevant tests, but complete termination of the full test suite was not conclusively established in the audit environment.

### Impact

This does not constitute evidence of a software vulnerability.

It limits the confidence that can be assigned to the complete automated regression suite as executed during the audit.

### Recommendation

Run the complete test suite in a supported environment and record:

- total tests collected;
- total tests passed;
- skipped tests;
- failures;
- duration;
- final process exit status.

For release validation, the complete suite should terminate with a successful exit code.

# 8. Terminal Backend Compatibility — Documentation Recommendation

**Status:** No security finding

The plugin currently needs to determine characteristics of the Hermes terminal backend for compatibility purposes.

This is not considered a violation of the plugin configuration API.

The terminal backend is a **host execution property**, rather than a plugin setting. The available Hermes plugin API does not provide a supported plugin-facing configuration API that exposes this information.

Accordingly, the current mechanism should be retained as an intentional compatibility solution.

### Documentation recommendation

The plugin documentation should explicitly state:

1. why terminal-backend detection is required;
2. why the current mechanism is used;
3. that the value is a host execution property rather than plugin configuration;
4. that no supported Hermes plugin API currently exposes the required information;
5. that the implementation should migrate to an official Hermes API if one becomes available in the future.

This should be treated as a **compatibility/documentation note**, not as a security finding.

# 10. Secret Handling and Data Flow

The plugin follows a deliberate READ/WRITE asymmetry.

### READ operations

Retrieved secrets are represented using opaque placeholders rather than being directly returned to the LLM.

This substantially reduces the risk of accidental secret disclosure through normal tool responses.

### WRITE operations

The design permits explicit direct password/pass input as an exception, while encouraging:

- secure `*_file` inputs;
- generated credentials;
- dual-channel warnings.

This is an appropriate distinction because writing a secret necessarily creates a fundamentally different interaction model from retrieving one.

### Placeholder handling

The placeholder registry provides:

- single-use semantics;
- atomic consumption;
- mutex protection;
- consistent substitution of repeated occurrences;
- temporary-file materialization where required.

This is a strong security boundary because placeholder resolution happens immediately before execution rather than exposing the underlying secret to the LLM.

---

# 11. Filesystem Security

The plugin applies significant filesystem hardening to security-sensitive paths.

Relevant protections include:

- strict permissions on the secrets directory;
- owner validation;
- rejection of symlinked sensitive directories;
- restrictive permissions on bootstrap secret files;
- hardened Bitwarden application data;
- validation of the Bitwarden CLI executable;
- protection against group/world-writable executables.

These controls are appropriate for a deployment-agnostic Linux plugin.

The remaining concern is primarily the race resistance of file-based secret input, addressed in **HVA-03**.

---

# 12. Subprocess Security

The Bitwarden CLI integration is one of the plugin's most security-sensitive components.

The implementation uses an isolated environment rather than inheriting the complete parent environment.

This is important because the parent environment may contain unrelated credentials or sensitive configuration.

`BW_SESSION` is maintained in memory and supplied only to the isolated subprocess environment.

This materially reduces the risk of accidental exposure through:

- command-line arguments;
- persistent environment configuration;
- shell history;
- normal process invocation logging.

The subprocess wrapper therefore represents a strong security boundary.

---

# 13. Shell Injection Resistance

The plugin's file-based secret injection mechanism uses shell-safe quoting for generated paths and rejects control-character paths.

This is important because secret-file paths ultimately participate in command execution.

The implementation's fail-closed behavior for malformed paths is appropriate.

No evidence was identified that direct secret values are intentionally interpolated into shell command strings as ordinary untrusted text.

---

# 14. Lifecycle and Concurrency

The scoped redaction design uses reference counting and synchronization to support overlapping executions.

This is particularly important for an Agent host where multiple tool executions may occur concurrently.

The use of execution-scoped secret handling and context-local state reduces the risk that one execution accidentally releases or corrupts another execution's secret state.

The SSH-specific lifecycle issue identified in **HVA-01** is therefore an inconsistency with an otherwise stronger lifecycle architecture.

---

# 15. Third-Party Integration Risk

The plugin depends on two important external components:

### Bitwarden CLI

The plugin delegates Vaultwarden operations to the `bw` executable.

Security therefore depends partly on:

- the authenticity of the installed CLI;
- executable permissions;
- executable ownership;
- version compatibility;
- CLI behavior;
- the security of the underlying host.

The plugin mitigates some of these risks through executable validation and version/capability detection.

### Vaultwarden

Vaultwarden remains an external security boundary.

The plugin cannot independently guarantee:

- server-side authentication security;
- Vaultwarden server security;
- TLS endpoint integrity beyond normal HTTPS validation;
- server-side access controls;
- Vaultwarden database security.

The plugin should therefore be considered a client-side security layer rather than a replacement for Vaultwarden server security controls.

---

# 16. Reliability and Failure Handling

The plugin generally favors fail-closed behavior for security-critical conditions.

Examples include:

- missing lifecycle hooks;
- invalid filesystem state;
- invalid secret directories;
- missing bootstrap secrets;
- unsupported CLI capabilities;
- invalid configuration;
- unavailable authoritative result transformation.

This is preferable to attempting to continue operation with an unknown security state.

Cleanup failures are also surfaced in sanitized form rather than silently ignored.

---

# 17. Performance Considerations

The principal security mechanisms introduce modest overhead through:

- placeholder lookup;
- secret registration;
- redaction;
- filesystem validation;
- subprocess environment construction;
- lifecycle bookkeeping.

These operations are expected to be small compared with the latency of Bitwarden CLI and Vaultwarden operations.

The current design does not present an obvious performance bottleneck that would justify weakening the security controls.

The main performance-related concern is potential growth of the redaction registry if the SSH lifecycle issue in **HVA-01** is exercised repeatedly.

---

# 18. Code Quality and Maintainability

The architecture demonstrates good separation of responsibilities.

Notable separations include:

- configuration;
- authentication/session management;
- CLI invocation;
- placeholder resolution;
- secret-source handling;
- security/redaction;
- lifecycle hooks;
- filesystem hardening;
- compatibility detection;
- tool handlers.

This separation is beneficial for security review because security-sensitive behavior is concentrated into identifiable modules.

The primary maintainability recommendation is to make secret lifecycle ownership explicit wherever a secret enters the redaction system.

---

# 19. Supply-Chain Considerations

The plugin itself uses Python standard-library functionality rather than introducing a substantial third-party Python dependency chain.

The primary external executable dependency is the Bitwarden CLI.

The security posture therefore depends heavily on how `bw` is installed and maintained.

Deployment documentation should recommend:

- obtaining the CLI from a trusted distribution source;
- verifying the expected executable;
- maintaining a supported CLI version;
- avoiding writable locations for the executable;
- restricting write access to the executable and its parent directories.

The plugin's executable ownership and permission validation provide an additional defense layer.

---

# 20. Privacy Assessment

The plugin handles highly sensitive information by design.

The strongest privacy-preserving controls are:

- opaque secret placeholders;
- authoritative output redaction;
- isolated subprocess environments;
- memory-only session-key handling;
- avoidance of secret values in argv;
- secure temporary secret files;
- restricted bootstrap secret files;
- sanitized logging.

The main privacy concerns identified are:

- unnecessary lifetime of SSH-related registered secrets (**HVA-01**);
- potentially sensitive URL components (**HVA-02**).

---

# 21. Recommended Remediation Priority

### Priority 1 — HVA-01

Audit all SSH secret registration paths and guarantee deterministic release.

This should be treated as the highest priority because it directly concerns plaintext secret lifetime.

### Priority 2 — HVA-02

Restrict `server_url` to the minimum necessary URL structure and prevent sensitive URL components from entering logs or diagnostics.

### Priority 3 — HVA-03

Strengthen file-based secret handling against symlink and TOCTOU attacks.

### Priority 4 — HVA-04

Harden SSH temporary socket cleanup so cleanup can only affect objects demonstrably created by the current execution.

### Priority 5 — HVA-05

Record and verify complete test-suite execution in a supported environment.

### Documentation

Document the terminal-backend detection mechanism as an intentional compatibility exception and identify an official Hermes API as the preferred future migration path if one becomes available.

---

# 22. Final Assessment

`hermes-vaultwarden-plugin` v0.6.9 demonstrates a security-conscious architecture for integrating Vaultwarden with an LLM agent environment.

The most significant positive characteristic is that the implementation does **not** treat ordinary subprocess execution as the security boundary. Instead, it establishes multiple layers:

1. secret isolation;
2. opaque placeholder representation;
3. controlled secret materialization;
4. isolated subprocess environments;
5. authoritative output transformation;
6. lifecycle-scoped redaction;
7. filesystem hardening;
8. fail-closed initialization and execution.

This layered approach substantially reduces the likelihood that Vaultwarden secrets will accidentally enter the LLM context or ordinary logs.

The identified weaknesses are principally lifecycle and hardening issues rather than fundamental architectural flaws.

### Overall security rating: **MEDIUM**

The plugin is suitable for continued development and controlled use, subject to remediation of the identified findings and continued regression testing.

The most important remediation is to ensure that every secret registered for redaction has a clearly bounded lifetime, particularly in SSH-related execution paths.

The terminal-backend detection mechanism does **not** constitute a security finding. It should instead be documented as an intentional compatibility mechanism based on the current Hermes Agent API surface.
