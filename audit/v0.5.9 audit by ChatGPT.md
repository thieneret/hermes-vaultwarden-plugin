# Independent Security Audit
## hermes-vaultwarden-plugin v0.5.9

**Host:** Hermes Agent 2026.10.x  
**Plugin:** vaultwarden / hermes-vaultwarden-plugin  
**Third-party integration:** Bitwarden CLI (`bw`) + Vaultwarden  
**Language:** Python 3.10+, stdlib runtime  
**Deployment:** Linux / Docker / gateway mode  
**Audit basis:** v0.5.9 source tree supplied for audit

---

# 1. Executive Summary

**Overall risk: MEDIUM**

The v0.5.9 implementation is substantially security-conscious and the major architectural security fixes are present in the source.

In particular:

- **SEC-01 is correctly implemented architecturally.** Secret-result redaction is performed in `transform_tool_result`, and `post_tool_call` is observer/cleanup oriented rather than being relied upon as the confidentiality boundary.
- **SEC-02 is correctly implemented in the placeholder registry and middleware.** A placeholder is atomically consumed once, and multiple occurrences in the same command are rewritten to the same temporary file.
- The v0.5.8 secrets-directory validation itself correctly checks **symlink status, ownership and exact `0700` permissions**.
- Temporary-file cleanup failures are now observable and sanitized.
- The Bitwarden CLI is executed from a pinned absolute path with substantial binary validation.
- Subprocess environments are explicitly constructed rather than inheriting the complete parent environment.
- Bootstrap credentials are kept out of the normal OS environment.
- The default local-terminal policy is appropriately fail-closed.

However, the audit identified several genuine issues that prevent an `ACCEPTABLE` or `LOW` rating:

1. **The configured Vaultwarden server URL is not required to use HTTPS.** The plugin can therefore be configured to transmit API credentials/master-password-derived authentication traffic to an `http://` endpoint.
2. **Vault secrets resolved through placeholders are registered in the global redaction filter but are never forgotten.** This defeats the intended per-execution lifetime and causes plaintext secret retention in process memory.
3. **The v0.5.8 directory validation is not actually a plugin-load fail-closed condition.** Startup cleanup suppresses validation errors, and registration does not eagerly validate the directory. The plugin can therefore report itself active despite an invalid secrets directory; failure occurs only when injection is later attempted.
4. **The Bitwarden appdata directory lacks the equivalent strict ownership/symlink validation applied to the secret-injection directory.**
5. **The shell command generated for file injection contains an unescaped filesystem path.** A maliciously constructed `XDG_RUNTIME_DIR`/temporary-directory path could become shell syntax inside `$(< path)`.
6. **Failure to register `post_tool_call` or `on_session_end` does not cause plugin registration to fail**, leaving cleanup/lifecycle guarantees degraded.
7. A runtime log message exposes the exact Bitwarden CLI version, contrary to the stated requirement that runtime logs contain no version numbers.

These are primarily hardening and deployment-boundary issues rather than evidence of a trivial remote compromise. Nevertheless, this plugin handles highly sensitive credentials, so the security bar should remain high.

# 3. Detailed Analysis

## AUD-01 — HTTPS is not enforced

### Issue

`PluginConfig.validate()` verifies that `server_url` is present but does not constrain its scheme.

The value eventually reaches:

```text
bw config server <server_url>
```

and the Bitwarden CLI subsequently performs API-key authentication and vault operations against that configured server.

The official Bitwarden documentation shows self-hosted CLI configuration using HTTPS URLs and explicitly documents `https://your.bw.domain.com` as the normal server configuration.

### Why it matters

The bootstrap credentials include:

- Bitwarden API client secret
- master password

If an operator accidentally configures:

```text
http://vault.example.com
```

the plugin does not reject the configuration.

This turns a configuration mistake into a potentially catastrophic credential-disclosure condition.

### Fix

Require:

```text
https://
```

for normal deployments.

A reasonable exception would be an explicit configuration option for loopback-only development/testing, for example:

```text
allow_insecure_http_localhost: true
```

and even that should reject non-loopback hosts.

**Severity: HIGH.**

---

## AUD-02 — Resolved vault secrets remain in the global redaction registry

### Issue

`_resolve_placeholder_token()` does:

```text
get_redacting_filter().register_secret(value)
```

after fetching the vault secret.

The middleware later clears the task-scoped secret store:

```text
take_task_secrets(task_id)
```

but does **not** call:

```text
redactor.forget_secret(value)
```

for the placeholder-resolved secret.

### Why it matters

The code documentation repeatedly describes the injected secret as execution-scoped.

The actual implementation instead retains every resolved vault secret in the global `RedactingFilter` for the lifetime of the process.

Consequences include:

- indefinite plaintext secret retention in Python memory;
- memory growth proportional to the number of unique vault secrets accessed;
- unrelated future log/result strings can be replaced because they happen to contain an old secret;
- the global filter becomes a long-lived plaintext secret collection.

This is especially inconsistent with the otherwise careful ContextVar lifecycle design.

### Fix

Prefer a scoped per-execution redaction set.

If the global filter must be used as defense-in-depth, record exactly which secrets were registered by the current middleware execution and remove them in the appropriate final cleanup stage.

Care is required not to remove a value while another concurrent execution is still using the same value.

**Severity: MEDIUM.**

---

## AUD-03 — Directory validation is not actually load-time fail-closed

### Issue

The `_validate_secrets_dir()` implementation itself is good.

It checks:

- symlink status;
- owner;
- exact `0700` mode.

However `_cleanup_stale_secrets()` catches directory-access/validation failures and simply returns.

The registration sequence calls:

```text
_cleanup_stale_secrets(...)
```

but does not then perform an explicit mandatory `_secrets_dir()` validation before declaring the plugin active.

Therefore an invalid secrets directory can exist while plugin registration still succeeds.

### Why it matters

The stated security contract says directory-validation failure must cause plugin load failure.

The current behavior is weaker:

```text
invalid directory
        ↓
plugin can still load
        ↓
placeholder injection eventually attempts _secrets_dir()
        ↓
only then does it fail
```

That creates a misleading active-plugin state and leaves non-terminal tools available under a security posture the registration contract says should be rejected.

### Fix

During `register()`:

1. create/validate the directory;
2. allow `SecurityError` to abort registration;
3. retain the injection-time validation as defense in depth.

**Severity: MEDIUM.**

---

## AUD-04 — `.bw-data` lacks equivalent strict validation

### Issue

`ensure_appdata_dir()` currently:

1. expands the path;
2. calls `mkdir(..., exist_ok=True)`;
3. calls `chmod(0700)`.

It does not reject:

- a symlink;
- an unexpected owner;
- an existing non-directory target;
- a directory whose parent/path can be manipulated by a lower-trust actor.

### Why it matters

The Bitwarden CLI's isolated appdata contains sensitive local CLI state.

The Bitwarden documentation confirms that `BITWARDENCLI_APPDATA_DIR` controls the CLI's separate account/configuration storage.

The secret-injection directory has substantially stronger validation than `.bw-data`, creating an inconsistent security boundary.

### Fix

Create a shared hardened-directory primitive and use it for:

- `vw-secrets`;
- `.bw-data`;
- potentially the SSH-agent socket directory.

Validate:

- non-symlink;
- directory;
- expected owner;
- exact `0700`.

**Severity: MEDIUM.**

---

## AUD-05 — Unescaped temporary-file path in shell substitution

### Issue

The middleware rewrites:

```text
$__VW_SECRET_x__
```

to:

```text
$(< /path/to/file)
```

The path is inserted directly.

### Why it matters

The path is derived from runtime/environment configuration:

```text
XDG_RUNTIME_DIR
```

or the system temporary-directory mechanism.

If the path contains shell syntax, the resulting terminal command can change its meaning.

For example, a malicious runtime directory containing shell metacharacters could turn:

```text
$(< /some/path)
```

into a larger shell expression.

This is primarily an environment/deployment-boundary attack rather than a normal remote attack, but command construction should never depend on the path being benign.

### Fix

Quote the path as a shell word before inserting it.

Also add regression tests for:

- spaces;
- `'`;
- `"`;
- `$`;
- backticks;
- `;`;
- `&`;
- parentheses;
- newline characters.

**Severity: MEDIUM.**

---

## AUD-06 — Lifecycle hook registration is not fully fail-closed

`transform_tool_result` registration is correctly fail-closed.

However:

```text
hooks_ok = register post_tool_call
hooks_ok &= register on_session_end
```

is not subsequently enforced.

If either registration fails, the plugin merely skips:

```text
Cleanup hooks registered
```

and continues as active.

### Consequences

If `on_session_end` cannot be installed:

- session cleanup becomes dependent on normal timeout/process lifecycle;
- placeholders may remain longer than expected;
- cleanup state is less deterministic.

If `post_tool_call` fails:

- placeholder cleanup/error surfacing changes.

This does not invalidate SEC-01 because the authoritative transformer is handled separately, but it weakens lifecycle guarantees.

### Fix

Treat `on_session_end` as mandatory.

Consider treating `post_tool_call` as mandatory too if its cleanup/error-reporting functions are part of the supported security contract.

**Severity: MEDIUM.**

---

## AUD-07 — Runtime version disclosure

`bw_cli.py` contains:

```text
log.info("bw CLI version %s validated (minimum: %s)", version_str, min_str)
```

The audit specification explicitly requires runtime logs to contain neither audit codes nor version numbers.

This is a straightforward compliance-with-design-intent defect.

**Severity: LOW.**

---

## AUD-08 — `secrets.yaml` should have stronger filesystem validation

The file is correctly required to be `0600`.

However:

- symlink status is not explicitly rejected;
- ownership is not checked.

A stronger implementation would make the bootstrap-secret file follow the same philosophy as the hardened directories.

This is less severe because the default local backend policy already recognizes the same-user threat and refuses local execution unless explicitly enabled.

**Severity: LOW/MEDIUM.**

# 4. Prior Audit Remediation Verification

## SEC-01 — Authoritative `transform_tool_result` redaction

### Verdict: **CORRECT in source**

The implementation has the right architecture.

The middleware:

1. resolves the placeholder;
2. creates the temporary file;
3. publishes the injected plaintext set;
4. invokes `next_call()`;
5. restores the ContextVar in `finally`.

The transformer:

1. obtains the execution-specific secrets;
2. replaces exact plaintext occurrences;
3. applies global redaction;
4. **returns the sanitized result**.

`post_tool_call` no longer serves as the confidentiality boundary.

This is the correct remediation.

### Remaining concern

The actual end-to-end test could not be completed in this audit environment because the focused E2E test timed out.

Therefore:

**Static implementation: PASS**  
**Dynamic E2E verification: INCOMPLETE**

The fail-closed capability check for a host without `transform_tool_result` is present and was also covered by the test source.

---

## SEC-02 — Atomic placeholder resolution

### Verdict: **CORRECT in source**

`PlaceholderRegistry.consume_and_resolve()` holds the registry lock while:

1. finding the entry;
2. checking expiry;
3. checking the used state;
4. marking it used;
5. returning the entry.

The middleware extracts unique tokens first and then performs exactly one atomic consume operation per token.

All occurrences are subsequently replaced using the same generated temporary-file path.

Therefore:

```text
TOKEN TOKEN TOKEN
```

becomes effectively:

```text
$(< same-file) $(< same-file) $(< same-file)
```

rather than three independent resolutions.

Cross-tool reuse is rejected.

### Testing status

The basic placeholder test suite passed:

```text
9 passed
```

The dedicated multi-occurrence hook test timed out in the audit environment, so dynamic confirmation of the complete middleware pipeline remains incomplete.

**Static implementation: PASS**  
**Focused registry tests: PASS**  
**Full middleware dynamic test: INCOMPLETE**

# 5. Third-Party Integration Risk Assessment

## Bitwarden CLI trust

The use of the official Bitwarden CLI is appropriate.

The CLI officially supports:

- API-key authentication using `BW_CLIENTID` / `BW_CLIENTSECRET`;
- `unlock --passwordenv`;
- isolated appdata using `BITWARDENCLI_APPDATA_DIR`;
- `bw config server`;
- `bw sync`;
- encoded JSON for create/edit operations.

The plugin's use of these interfaces is therefore broadly aligned with the documented CLI model.

Bitwarden's current release information also shows CLI 2026.9.1 in the 2026.9 release cycle and CLI 2026.10.0 in the current 2026.10 cycle, so the plugin's minimum of 2026.9.1 is not inherently unreasonable.

## Binary handling

The plugin performs unusually strong validation:

- absolute path required;
- symlink chain rejected;
- regular-file requirement;
- executable requirement;
- no group/world write;
- owner must be root/euid.

This is a strong control.

### Remaining TOCTOU concern

Validation and execution are separate filesystem operations.

A sufficiently privileged local attacker who can manipulate the containing directory could potentially replace the validated executable after validation but before a later execution.

The practical risk is significantly reduced when the binary resides in a root-owned, non-writable directory such as a properly protected `/usr/local/bin`.

A future hardening step should therefore also document and/or validate the ownership/permissions of the binary's parent directory.

# 6. Reliability and Performance

The implementation is generally well structured.

Positive observations:

- `BwCli` subprocesses have explicit timeouts.
- Network retries are limited.
- Non-idempotent authentication/mutation operations are excluded from retry.
- Session recovery is explicit.
- Placeholder registry operations are mutex protected.
- ContextVar restoration uses tokens rather than global clearing.
- Temporary resources are generally cleaned in `finally`.
- The plugin defers authentication until first use.

One issue worth addressing is the lifecycle-hook failure handling described in AUD-06.

Another practical concern is that configuration values such as retry counts/backoff values are converted but not strongly range-validated. For example, negative retry/backoff values can be supplied. This is not currently a major security issue, but stricter configuration validation would improve predictability.

---

# 7. Dependency and Supply-Chain Assessment

The runtime dependency posture is strong:

- Python standard library only;
- no runtime PyPI dependency;
- Bitwarden CLI is an explicit external binary.

The development environment does contain pytest/ruff/mypy dependencies, but these are not runtime dependencies.

The primary supply-chain boundary is therefore the pinned `bw` executable.

The plugin correctly avoids PATH-based discovery and rejects symlinks.

Recommended improvement:

- document SHA-256 verification of the deployed `bw` binary;
- preferably verify a deployment-time checksum/signature;
- ensure the containing directory is root-owned and not writable by the Hermes runtime user.

Bitwarden itself publishes CLI builds and checksum information through its distribution pipeline.

---

# 8. Privacy and Data Handling

The plugin handles extremely sensitive data:

- passwords;
- API keys;
- TOTP values;
- SSH private keys;
- SSH passphrases;
- Bitwarden API credentials;
- Bitwarden session keys.

The general data-minimization architecture is good:

- vault secrets are represented to the LLM by opaque placeholders;
- generated passwords are written directly to the vault;
- session keys remain in memory;
- subprocess environments are minimized;
- secret-bearing temporary files are short-lived.

The main privacy defect is AUD-02: resolved vault values remain registered in the global redactor indefinitely.

That should be fixed before considering the implementation fully compliant with its own memory-lifetime model.

# 9. Recommended Remediation Plan

## Immediate fixes

### 1. Enforce HTTPS

Reject any non-HTTPS `server_url` by default.

Allow HTTP only through an explicit development-only exception restricted to loopback.

**Priority: P0**

### 2. Fix global secret retention

Every placeholder-resolved secret must have a defined lifetime.

Do not leave it permanently in `RedactingFilter._secrets`.

Use an execution-scoped structure or reference-counted registration.

**Priority: P0**

### 3. Make secrets-directory validation genuinely load-time fail-closed

Change registration to explicitly validate the directory before the plugin becomes active.

Do not suppress `SecurityError` from the startup validation path.

**Priority: P1**

### 4. Shell-escape injected file paths

Never construct:

```text
$(< {raw_path})
```

with an unquoted filesystem path.

Add malicious-path regression tests.

**Priority: P1**

---

## Short-term improvements

### 5. Harden `.bw-data`

Apply:

- symlink rejection;
- owner validation;
- exact `0700`;
- directory-type validation.

**Priority: P1**

### 6. Harden `secrets.yaml`

Reject symlinked files and unexpected ownership.

**Priority: P1**

### 7. Make lifecycle-hook failures explicit

At minimum:

```text
on_session_end registration failure -> plugin load failure
```

Preferably make all security-relevant lifecycle hooks mandatory.

**Priority: P1**

### 8. Remove version information from runtime logs

Change the `bw` version log to a generic validation message.

**Priority: P2**

---

## Long-term improvements

### 9. Eliminate filesystem-path shell substitution where possible

The strongest architecture would avoid constructing shell syntax from filesystem paths altogether.

If Hermes permits direct argv-based execution for terminal integrations, use argv rather than shell text.

### 10. Add binary integrity verification

Document or implement checksum/signature verification for the deployed `bw` binary.

### 11. Add adversarial filesystem tests

Test:

- XDG runtime directory symlink;
- parent-directory replacement;
- malicious runtime-directory names;
- appdata symlink;
- appdata ownership mismatch;
- secrets.yaml symlink;
- secrets.yaml ownership mismatch;
- binary replacement between validation and execution.

### 12. Add concurrency tests for the complete redaction pipeline

Especially:

- two simultaneous calls with no task ID;
- two calls with identical secret values;
- transformer executing on another thread;
- transformer called more than once;
- cleanup racing with transformation.

# 11. Final Assessment

The v0.5.9 codebase demonstrates a substantial improvement in security architecture.

Most importantly:

**SEC-01: VERIFIED CORRECT IN CODE**  
The confidentiality boundary is correctly located at `transform_tool_result`, and the observer is no longer relied upon for redaction.

**SEC-02: VERIFIED CORRECT IN CODE**  
`consume_and_resolve()` provides atomic single-use semantics, and the middleware performs one resolution per unique placeholder and one shared temp file per token.

**v0.5.8 directory validation: PARTIALLY VERIFIED**  
The validation algorithm itself is correct, but the required plugin-load fail-closed integration is incomplete.

**v0.5.8 cleanup observability: VERIFIED**  
Deletion failures are caught and sanitized.

**v0.5.9 E2E coverage: PRESENT BUT NOT DYNAMICALLY VERIFIED**  
The test scenario is appropriate, but execution timed out in this audit environment.

The implementation should **not be considered security-complete yet** because the HTTPS enforcement and global secret-retention problems affect the core confidentiality model. After those issues are corrected, the remaining findings are primarily hardening and lifecycle robustness concerns.
