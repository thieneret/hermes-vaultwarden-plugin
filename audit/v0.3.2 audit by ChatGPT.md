## 1. Executive summary

**Overall risk: HIGH — not production-ready without remediation.**

I audited the supplied specification/logs together with the current public source of `hermes-vaultwarden-plugin` and the relevant Hermes plugin API documentation. The plugin has a **thoughtful security architecture**—especially placeholder-based secret delivery, subprocess environment minimization, in-memory session handling, explicit write gating, structured errors, and SSH-key temporary-file protection. The repository itself also explicitly warns that it was AI/vibe-coded and should be audited before production. [GitHub](https://github.com/thieneret/hermes-vaultwarden-plugin)

However, the security boundary is unusually sensitive because this plugin can retrieve **passwords, tokens, TOTP values and SSH private keys** and can inject them into terminal commands. That means relatively small integration mistakes can become full credential compromise.

The most important issues I found are:

1. **`bw`, `ssh-add`, `ssh-agent`, and `ssh-keygen` are not cryptographically pinned or necessarily absolute-path pinned** → a compromised `PATH` can turn the trusted CLI boundary into arbitrary-code execution.
2. **SSH-agent socket handling accepts attacker/model-controlled paths and can start an agent at that location** → this deserves hardening because it crosses from secret management into local process/socket control.
3. **The configuration implementation still performs raw `config.yaml` parsing despite the native Hermes configuration API being available** → compatibility workaround, but it weakens isolation and maintainability and contradicts the intended host API model. Current Hermes explicitly provides plugin-namespaced `ctx.get_config()`. [fossies.org](https://fossies.org/dox/hermes-agent-2026.9.24/classhermes__cli_1_1plugins_1_1PluginContext.html?utm_source=chatgpt.com)
4. **The plugin's CI lint stage is non-blocking**, meaning known static-analysis defects do not prevent merges. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/.github/workflows/ci.yml)
5. **There is no demonstrated dependency/third-party binary integrity policy** for `bw` or OpenSSH.
6. **The placeholder security model is strong but inherently fragile at the middleware boundary**: it depends on every relevant terminal execution path being intercepted and on the configured tool/argument names remaining complete.
7. **The plugin has no evidence in the supplied material of a complete production-grade integration test against real Hermes + real `bw` + Vaultwarden + real SSH-agent behavior.**

The supplied audit specification correctly identifies the critical data and threat model: the plugin handles vault credentials, API keys, SSH private keys and the Bitwarden session key, while requiring placeholder injection, environment isolation, log redaction and fail-closed authentication. # 3. Detailed analysis

## 3.1 Architecture and execution flow

The architecture is broadly:

```text
Hermes Agent
    │
    ├── plugin register(ctx)
    │       │
    │       ├── load configuration
    │       ├── resolve bootstrap credentials
    │       ├── remove bootstrap env variables
    │       ├── create isolated bw appdata
    │       ├── create AuthManager
    │       ├── register 13 tools
    │       └── register placeholder middleware/hooks
    │
    ├── vaultwarden_* tool
    │       │
    │       └── AuthManager
    │               │
    │               └── BwCli
    │                       │
    │                       └── `bw` subprocess
    │
    └── terminal tool
            │
            └── tool_request middleware
                    │
                    ├── consume placeholder
                    ├── fetch vault field
                    ├── escape secret
                    └── substitute secret immediately before execution
```

This is a sensible architecture for keeping ordinary vault values out of the model context. The repository describes the same design: metadata and placeholders are exposed to the LLM, while the actual secret is resolved immediately before terminal execution. [GitHub](https://github.com/thieneret/hermes-vaultwarden-plugin)

The registration path also deliberately performs lazy authentication so plugin loading does not block Hermes startup. The source explicitly says authentication is deferred to first use and aims to stay within the host's plugin-load timeout. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/__init__.py)

That is a good design choice.

---

## 3.2 Strong point: placeholder implementation

This is one of the better parts of the plugin.

The placeholder registry:

- uses `secrets.token_hex(6)`;
- has a 48-bit token space;
- stores only `(item_id, field)`, not the secret;
- has TTL;
- limits the number of outstanding placeholders;
- uses a `threading.Lock`;
- atomically consumes tokens;
- clears them at session termination. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/placeholders.py)

The critical sequence is also correct conceptually:

```text
placeholder
    ↓
consume atomically
    ↓
retrieve vault value
    ↓
inject
    ↓
redact
    ↓
forget
```

This substantially reduces accidental model-context exposure.

### Important limitation

The security does **not** come from the placeholder itself. It comes from the **Hermes middleware intercepting the eventual execution**.

That distinction is important.

If a secret placeholder is passed to an execution mechanism that the plugin does not recognize, the security guarantee changes. The middleware explicitly recognizes a configured set of terminal tools and command argument keys. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/hooks.py)

Therefore:

> **The plugin must never claim “secrets cannot enter context” without also guaranteeing that every secret-consuming execution path is intercepted.**

This is why I rated VWP-03 HIGH.

# 4. VWP-01 — Binary trust boundary is insufficiently pinned

This is the most important technical finding.

`bw_cli.py` resolves the Bitwarden executable as:

1. explicitly configured path;
2. `BW_CLI_PATH`;
3. `shutil.which("bw")`. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/bw_cli.py)

The same general issue exists for:

- `ssh-add`
- `ssh-agent`
- `ssh-keygen`

because those are invoked by executable name.

For a normal application this is often acceptable.

For a **password-vault integration**, it is not enough.

If the process `PATH` is modified so that an attacker-controlled `bw` appears first, the plugin will willingly execute it with:

```text
BW_CLIENTID
BW_CLIENTSECRET
BW_MP
BW_SESSION
```

depending on the operation.

That converts a binary replacement into credential theft.

The plugin's minimal environment helps, but it does **not** solve binary substitution.

### Recommended production policy

Require:

```text
bw_cli_path = /usr/local/bin/bw
```

and verify:

- regular file;
- executable;
- expected owner;
- expected group;
- no group/world write;
- optionally expected SHA-256;
- optionally package-manager provenance.

For the highest-security installation, pin the exact `bw` version and checksum.

Do the same for OpenSSH binaries.

# 5. VWP-02 — SSH-agent socket control needs hardening

The SSH feature is powerful because it can load a private key directly into an agent.

The problematic path is:

```text
ssh_auth_sock
    ↓
_resolve_socket_path()
    ↓
ssh-agent -a <user-controlled-path>
```

The source accepts a direct path and can start a new agent there. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/tools.py)

This is not immediately equivalent to arbitrary file write, so I would **not** classify it as CRITICAL. But it is a significant privilege boundary.

The model/user can potentially influence:

- where the agent socket is created;
- which existing socket is contacted;
- whether a new agent is started.

### Recommended restrictions

Only permit:

```text
$XDG_RUNTIME_DIR/...
/run/user/<uid>/...
```

or an explicitly administrator-approved SSH-agent socket.

Reject:

```text
/etc/...
/root/...
/home/other-user/...
relative paths
regular files
paths outside approved runtime directories
```

Also verify the resulting socket's:

- owner;
- type;
- permissions.

# 6. VWP-04 — Secret injection into command strings

The plugin does careful escaping:

- `shlex.quote()` for shell context;
- URL percent encoding for URL contexts;
- conservative handling of ambiguous contexts. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/security.py)

That is good.

But the fundamental operation remains:

```text
secret → plaintext command string
```

This is inherently fragile.

For example:

```text
curl -H 'Authorization: Bearer <secret>'
```

means the secret exists in the command representation immediately before execution.

Even if Hermes does not expose that string to the model, it may be visible to:

- subprocess tracing;
- audit middleware;
- debugging middleware;
- exception objects;
- shell instrumentation;
- process wrappers;
- future plugins;
- command history, depending on execution backend.

### Better architecture

Prefer:

```text
secret → environment variable
```

or:

```text
secret → stdin
```

or:

```text
secret → anonymous file descriptor
```

rather than:

```text
secret → command string
```

For example, conceptually:

```text
terminal(
    command="curl -H 'Authorization: Bearer $VW_SECRET'",
    secret_env={"VW_SECRET": placeholder}
)
```

would provide a substantially cleaner boundary.

# 7. Configuration compatibility

There is a particularly interesting discrepancy between the supplied audit material and the current source.

The supplied material says a raw configuration fallback is required because `ctx.get_config()` does not expose `plugins.entries`. Beillesztett szöveg

The current Hermes API, however, explicitly provides namespaced `ctx.get_config()` access for plugin settings. [fossies.org](https://fossies.org/dox/hermes-agent-2026.9.24/classhermes__cli_1_1plugins_1_1PluginContext.html?utm_source=chatgpt.com)

The plugin currently tries:

1. `ctx.get_config()`;
2. `read_user_config_raw()`;
3. direct `~/.hermes/config.yaml` parsing;
4. object-style `.config` / `.plugin_config`. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/config.py)

This is understandable as backwards compatibility, but it is undesirable.

### Why?

A plugin should not need to understand the host application's filesystem layout.

Direct access to:

```text
$HERMES_HOME/config.yaml
```

creates coupling to:

- file location;
- YAML structure;
- migration behavior;
- future config encryption;
- profiles;
- permissions;
- host-side config transaction semantics.

Current Hermes documentation explicitly describes `ctx.get_config()` as the plugin-relative API and limits plugin access to its own namespace. [fossies.org](https://fossies.org/dox/hermes-agent-2026.9.24/classhermes__cli_1_1plugins_1_1PluginContext.html?utm_source=chatgpt.com)

### Recommendation

Set a minimum Hermes version and remove the filesystem fallback.

If old Hermes versions must remain supported:

```text
config_adapter.py
    ├── Hermes2026_9
    ├── HermesLegacy
    └── unsupported → fail closed
```

rather than having fallback logic embedded in normal configuration loading.

# 8. Error handling

This area is generally good.

The plugin:

- catches tool-level exceptions;
- returns structured JSON;
- avoids exposing subprocess arguments in generic errors;
- distinguishes binary/network/session/not-found/parse failures;
- has timeouts;
- retries network errors once;
- validates JSON response types. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/bw_cli.py)

The supplied error envelopes are also appropriately structured. Beillesztett szöveg

### But there is a weakness

Network/session classification depends heavily on matching strings returned by `bw`:

```text
"not logged in"
"vault is locked"
"certificate"
"network"
"fetch failed"
...
```

That is inherently version-dependent.

A CLI update can change:

```text
"Vault is locked"
```

to:

```text
"Your vault must be unlocked"
```

and alter the plugin's state machine.

### Recommendation

Maintain a compatibility table:

| bw version | tested | supported |
|---|---:|---:|
| X.Y | ✓ | ✓ |
| X.Z | ✓ | ✓ |
| future | ? | no |

and fail conservatively on unknown versions.

# 9. `vaultwarden_generate_password` is a real secret-exposure exception

The documentation calls this:

> “the only tool that returns a secret”

and the implementation returns the generated password directly. [GitHub](https://github.com/thieneret/hermes-vaultwarden-plugin)

This is not necessarily a bug.

It is, however, a **deliberate violation of the otherwise strong secret architecture**.

The model receives the password, meaning:

```text
Vault secret → placeholder
```

is protected, while:

```text
new secret → model context
```

is not.

That should be an explicit capability in the security model.

I would strongly recommend:

```text
vaultwarden_generate_password
    → generated secret
    → placeholder
```

rather than plaintext, unless the use case genuinely requires model-visible output.

---

# 10. SSH private-key handling

This portion is comparatively strong.

The plugin uses:

```python
tempfile.mkstemp()
chmod(0600)
...
finally:
    os.unlink()
```

and passes the passphrase through stdin rather than a temporary file. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/tools.py)

That satisfies the important properties in the supplied requirements.

There is nevertheless a weakness in `_agent_running()`:

```python
env={**os.environ, "SSH_AUTH_SOCK": sock}
```

This is inconsistent with the very good `bw` subprocess model.

The `bw` environment is explicitly minimized:

```text
PATH
HOME
BITWARDENCLI_APPDATA_DIR
BW_SESSION / credentials as required
```

while `ssh-add -l` receives the complete process environment. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/bw_cli.py)

### Fix

Use:

```text
PATH
HOME
SSH_AUTH_SOCK
```

only.

This should be considered mandatory if the host process can contain unrelated credentials.

# 11. CI / development quality

# 12. Third-party integration risk assessment

## Bitwarden CLI

**Trust level: acceptable with controls.**

Using the official `bw` CLI instead of implementing the Bitwarden protocol independently is sensible.

The plugin also isolates its `bw` environment and appdata, which is very good. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/bw_cli.py)

But the trust boundary is:

```text
Plugin
  ↓
bw binary
  ↓
Vaultwarden
```

and the plugin currently trusts the binary based largely on path resolution.

Therefore:

**`bw` itself: LOW/MEDIUM risk**

**`bw` binary supply chain: HIGH unless pinned**

---

## Vaultwarden server

The server is remote and therefore untrusted from the plugin's process perspective.

The plugin correctly treats malformed CLI output as an error rather than blindly deserializing arbitrary structures.

However, Vaultwarden availability, TLS validity and server behavior are still external dependencies.

The server URL should be required to use HTTPS except for an explicit development-only mode.

---

## OpenSSH

OpenSSH is mature and appropriate.

The problem is not primarily OpenSSH itself; it is the **way executable discovery and agent socket selection are delegated to runtime input**.

# 13. Recommended remediation plan

## 1. Immediate fixes

### A. Pin trusted executables

Change the production contract to:

```text
bw_cli_path = absolute path
```

and reject:

- PATH fallback;
- relative paths;
- writable binaries.

Do the equivalent for:

```text
ssh-add
ssh-agent
ssh-keygen
```

Prefer administrator-configured absolute paths.

### B. Lock down SSH-agent sockets

Permit only sockets inside an approved runtime directory.

Do not allow arbitrary agent socket creation.

### C. Remove full environment inheritance

Change:

```python
env={**os.environ, "SSH_AUTH_SOCK": sock}
```

to a minimal environment.

### D. Protect direct secret retrieval

Make:

```text
allow_direct_secret_retrieval
```

unavailable in production or require an explicit capability/approval.

### E. Treat middleware absence as a security failure

This is especially important.

Currently the plugin can log:

```text
Context lacks register_middleware; placeholder injection OFF.
```

That is potentially dangerous because the plugin is a secrets-management component.

For a production security profile:

> **If the placeholder middleware cannot be registered, the plugin should not activate secret-reference functionality.**

Fail closed.

---

## 2. Short-term improvements

### A. Replace raw config fallback

Move all configuration access to the Hermes plugin API.

Current Hermes supports namespaced configuration through `ctx.get_config()`. [fossies.org](https://fossies.org/dox/hermes-agent-2026.9.24/classhermes__cli_1_1plugins_1_1PluginContext.html?utm_source=chatgpt.com)

### B. Introduce a `BwCompatibility` layer

Centralize:

- version detection;
- supported versions;
- status interpretation;
- error mapping;
- command syntax.

### C. Make CI blocking

At minimum:

```text
pytest
ruff
mypy
pip-audit
bandit
```

must fail CI on errors.

### D. Add integration tests

Test against:

```text
Hermes
    +
real bw
    +
real Vaultwarden
    +
real ssh-agent
```

not only mocks.

### E. Test adversarial placeholders

Tests should include:

- placeholder embedded in single quotes;
- double quotes;
- backticks;
- `$()`;
- URL credentials;
- JSON;
- multiline shell;
- heredoc;
- escaped shell;
- multiple placeholders;
- repeated placeholders;
- expired placeholders;
- concurrent resolution;
- failed resolution;
- terminal backend unknown to plugin.

## 3. Long-term improvements

### A. Replace command-string secret injection

The ideal architecture is:

```text
LLM
 ↓
opaque secret reference
 ↓
Hermes execution capability
 ↓
secret passed through env/stdin/FD
 ↓
process
```

rather than:

```text
LLM
 ↓
opaque reference
 ↓
string substitution
 ↓
shell command containing plaintext
```

### B. Use a host-native secret capability

If Hermes provides a proper secret-injection interface in the future, migrate to it rather than maintaining a parallel middleware architecture.

### C. Add plugin release signing

For a credential plugin, production distribution should ideally use:

```text
signed release
+
immutable commit
+
SHA-256
+
known dependency set
```

rather than:

```text
git clone main
```

### D. Establish a formal threat model

The plugin needs explicit threat actors:

```text
T1: malicious LLM prompt
T2: malicious vault item
T3: compromised terminal command
T4: compromised bw binary
T5: malicious local user
T6: compromised Hermes plugin
T7: malicious Vaultwarden server
T8: concurrent plugin execution
```

and each should have an explicit mitigation.

# Final verdict

### **HIGH RISK — DO NOT DEPLOY WITH PRODUCTION SECRETS YET**

I would **not reject the architecture**. In fact, several design decisions are unusually good for an AI-agent secret plugin:

- no secret in normal model context;
- single-use placeholders;
- TTL;
- concurrency protection;
- minimal `bw` environment;
- in-memory session key;
- fail-closed placeholder resolution;
- explicit write gate;
- structured errors;
- `0600` SSH-key temporary files;
- passphrase through stdin;
- lazy authentication. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/placeholders.py)

But the **trust boundary is not yet tight enough for a password vault**.

The two changes I would consider most urgent are:

> **1. Pin and verify every privileged external executable.**  
> **2. Make the secret-injection middleware a mandatory security capability rather than an optional compatibility feature.**

After those, harden SSH-agent socket handling, remove raw Hermes config access, eliminate full environment inheritance, make CI security checks blocking, and add real end-to-end tests.

With those changes, I would expect the architecture to move from **HIGH** toward **MEDIUM/LOW**, subject to the missing runtime evidence and a final source-level review.
