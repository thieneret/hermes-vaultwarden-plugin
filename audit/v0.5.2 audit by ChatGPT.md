# 1. Executive summary

**Overall risk: HIGH**

I audited the supplied audit brief against the **current `main` branch of `thieneret/hermes-vaultwarden-plugin`**, including the v0.5.2 manifest and the relevant implementation files. The repository itself explicitly warns that it was AI/vibe-coded and should be audited before production use. [GitHub](https://github.com/thieneret/hermes-vaultwarden-plugin)

The architecture is substantially security-conscious: pinned `bw` binary validation, isolated Bitwarden appdata, memory-only session handling, `0600` secret files, placeholder indirection, atomic temporary files, and fail-closed middleware registration are all good decisions. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/bw_cli.py)

However, I found **several material issues**:

1. **HIGH — post-tool secret redaction is not fail-closed.** If `post_tool_call` cannot be registered, the plugin continues loading even though that hook is part of the mechanism preventing an injected secret echoed by a terminal command from reaching the LLM. The middleware itself is fail-closed, but the result-redaction layer is not. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/__init__.py)
2. **MEDIUM — placeholder single-use semantics can be bypassed within one command.** A repeated occurrence of the same placeholder can be consumed once but subsequently resolved again because `_inject_one()` uses `peek()`, which does not reject an already-used entry. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/hooks.py)
3. **MEDIUM — the optional startup SecretSource path appears broken in the repository state examined.** `__init__.py` imports `.secret_source`, while the corresponding source file was not present at the expected repository path. Enabling the option can therefore fail at registration time. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/__init__.py)
4. **MEDIUM — the security boundary depends strongly on terminal backend isolation.** With the local backend, the LLM runs as the same OS user and can directly read `secrets.yaml`. The project acknowledges this, but the plugin merely warns and remains active. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/secrets.py)
5. **LOW/MEDIUM — appdata isolation is weaker than the binary isolation.** The plugin enforces mode `700`, but does not perform an equivalent symlink/ownership/traversal validation on the Bitwarden appdata directory. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/auth.py)
6. **LOW — subprocess `PATH` remains inherited from the plugin process.** The environment is otherwise tightly allowlisted, but a fixed PATH would make the isolation claim stronger. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/bw_cli.py)

The supplied brief specifically identifies the repository as the audit target. Beillesztett szöveg(1)

# 3. Detailed analysis

## VW-01 — HIGH: post-tool redaction must be fail-closed

This is the most important issue I found.

The plugin correctly recognizes that the **injection middleware itself is security-critical** and refuses to operate when `tool_execution` middleware registration fails. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/__init__.py)

However, the same logic is not applied to `post_tool_call`.

The code does:

```text
hooks_ok = register_hook_if_available(... post_tool_call ...)
hooks_ok &= register_hook_if_available(... on_session_end ...)
if hooks_ok:
    log.info("Cleanup hooks registered")
```

There is no subsequent:

```text
if not hooks_ok:
    fail plugin
```

Instead, the plugin can remain active.

This matters because the middleware intentionally puts the plaintext secret into a temporary file and then executes:

```text
$(< /path/to/tempfile)
```

The command itself therefore has legitimate access to the plaintext. If the command does something like:

```text
printf '%s\n' "$(< /path/to/secret)"
```

the terminal tool can return the plaintext.

The plugin's protection against that reaching the LLM depends partly on its post-call secret redaction mechanism. The implementation explicitly records injected secrets per task for that purpose. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/hooks.py)

Hermes' current architecture has `post_tool_call` after execution and before result transformation/context insertion, so this is the correct security boundary. [GitHub](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/developer-guide/middleware.md?utm_source=chatgpt.com)

**Impact:** a compatibility failure can silently downgrade the plugin from “secret never reaches context” to “secret may reach context.”

**Fix:** treat `post_tool_call` as mandatory:

```python
if not compat.register_hook_if_available(...):
    raise RuntimeError(
        "Vaultwarden requires post_tool_call for secret redaction"
    )
```

`on_session_end` can reasonably be treated separately because losing it is primarily a cleanup/lifecycle problem rather than an immediate disclosure path.

## VW-02 — MEDIUM: single-use placeholder bypass

The registry correctly implements atomic consumption:

```text
entry.used = True
```

and documents single-use behavior. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/placeholders.py)

But the file-injection path does something subtly different:

1. `vaultwarden_inject_secrets()` calls `registry.consume()`.
2. `_inject_one()` subsequently calls `registry.peek()`.
3. `peek()` returns the entry even if `entry.used` is already `True`.

The relevant code is:

```text
registry.consume(placeholder)
...
_inject_one(...)
```

followed by:

```text
entry = registry.peek(placeholder)
```

and `peek()` only checks whether the entry exists and is expired; it does not reject `used=True`. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/hooks.py)

### Reproduction concept

Given one valid token:

```text
$__VW_SECRET_abcdef123456__
```

a command could contain it twice:

```text
printf '%s\n%s\n' "$__VW_SECRET_abcdef123456__" "$__VW_SECRET_abcdef123456__"
```

The first occurrence consumes the registry entry.

The second `consume()` fails, but `_inject_one()` can still `peek()` the same entry and retrieve the secret again.

So the effective behavior is:

> one placeholder → potentially multiple secret injections in the same execution.

This does **not** expose the secret to the model by itself, but it violates the stated single-use security invariant and makes replay semantics weaker than intended.

### Fix

The cleanest design is:

```text
entry = registry.consume(token)
value = resolve(entry)
```

with `_inject_one()` receiving the already-consumed entry.

Alternatively, change `peek()` to reject used entries—but that would require restructuring the current flow because the implementation currently depends on peeking after consumption.

## VW-03 — MEDIUM: optional SecretSource appears incomplete

The manifest advertises:

```text
allow_startup_secret_injection
```

and `__init__.py` contains:

```python
from .secret_source import register_secret_source
```

when that option is enabled. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/plugin.yaml)

In the repository state I inspected, however, the expected `plugins/vaultwarden/secret_source.py` was not available at that path.

Therefore:

```text
allow_startup_secret_injection: true
```

appears capable of producing an import failure during plugin registration.

This is not a vulnerability when the default is `false`, but it is a **broken advertised capability** and potentially a deployment-startup failure.

**Recommendation:** either ship and test the module or remove the option until it is actually supported.

---

## VW-04 — MEDIUM: local backend defeats the secret-file boundary

The v0.5.2 architecture has made a good improvement by moving bootstrap secrets from `.env` into:

```text
$HERMES_HOME/plugins/vaultwarden/secrets.yaml
```

and requiring mode `0600`. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/secrets.py)

But the security boundary is explicitly conditional.

With a local terminal backend:

```text
LLM → terminal → same OS user → secrets.yaml
```

The model can simply request:

```text
cat ~/.hermes/plugins/vaultwarden/secrets.yaml
```

The implementation acknowledges exactly this residual risk. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/secrets.py)

A warning is appropriate for development, but for a plugin whose stated security model is “secrets never enter the LLM context,” I would not consider **warning-only** sufficient for production.

### Recommendation

Prefer:

```text
local backend → plugin refuses to activate
```

and require an explicit override if someone deliberately wants this deployment mode.

That makes the security model enforceable instead of advisory.

---

## VW-05 — MEDIUM: appdata directory needs stronger validation

The plugin's binary validation is unusually strong. It rejects symlinks, non-regular files, writable binaries, and unexpected owners. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/bw_cli.py)

The Bitwarden data directory gets:

```text
0700
```

which is good. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/auth.py)

But the directory itself is not subjected to the same anti-symlink/ownership checks.

For example, a pre-existing:

```text
.bw-data -> /some/other/location
```

is not explicitly rejected.

This becomes relevant if the plugin ever runs with more privilege than the user controlling the directory.

**Recommendation:** apply the same principle used for `bw_cli_path`:

- reject symlinked path components;
- verify owner;
- verify directory mode;
- preferably create the directory under a trusted parent;
- reject a path outside the expected Hermes plugin data root unless explicitly configured.

# 4. Third-party integration risk assessment

## Bitwarden CLI (`bw`)

**Assessment: acceptable with controls.**

The integration is considerably better than a generic `subprocess` wrapper.

Positive controls include:

- absolute binary path;
- symlink rejection;
- owner validation;
- executable validation;
- group/world-write rejection;
- minimum version enforcement;
- isolated `BITWARDENCLI_APPDATA_DIR`;
- controlled subprocess environment;
- bounded subprocess timeout;
- retry policy;
- structured parsing;
- session/account/server verification. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/bw_cli.py)

The plugin also pins a minimum `bw` version of **2026.9.1**, which is appropriate for avoiding untested CLI behavior. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/compat.py)

The principal residual risk is that some behavior is inferred from CLI/server text strings rather than stable structured error codes. That's a compatibility concern rather than an immediate exploit.

## Malicious or replaced `bw`

The binary-pinning implementation is strong enough to substantially reduce the obvious replacement attack:

- PATH lookup is removed;
- environment override is removed;
- configured path must be absolute;
- symlink chains are rejected;
- file ownership is restricted;
- writable binaries are rejected. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/bw_cli.py)

That is one of the strongest parts of the implementation.

The remaining TOCTOU window between validation and execution is theoretically present, because validation and `execve` are separate operations. In a normal Docker deployment where the binary resides on a root-controlled filesystem this is low risk.

For a hostile filesystem, stronger measures would require descriptor-based execution or an immutable/container image.

## Vaultwarden server

The server should be considered **untrusted input**, even though the deployment normally assumes a trusted Vaultwarden instance.

The plugin does a reasonable job of parsing `bw` output and does not blindly deserialize arbitrary executable objects; JSON is parsed into normal Python objects. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/bw_cli.py)

The plugin also verifies the expected account identity against the configured `client_id`, which is a particularly good control against accidentally adopting another account's existing `bw` profile. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/auth.py)

# 5. Security architecture assessment

### Placeholder model

**Good, with the VW-02 defect.**

The registry is:

- memory-only;
- mutex protected;
- TTL bounded;
- size limited;
- cryptographically random;
- single-use by design. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/placeholders.py)

The main correction required is making resolution and consumption one atomic operation.

### File injection

**Good architecture.**

The current design avoids putting the actual secret into the command string:

```text
placeholder
    ↓
temporary 0600 file
    ↓
$(< file)
    ↓
shell
```

The file is created with `mkstemp`, permissions are explicitly changed to `0600`, and cleanup is performed in `finally`. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/hooks.py)

This is materially safer than the earlier direct substitution architecture.

### Session key

**Good.**

The session key is held in `AuthManager`, passed to `bw` via `BW_SESSION`, registered for redaction, and cleared when the session expires/locks. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/auth.py)

### Bootstrap secrets

**Good, but deployment-dependent.**

Moving secrets from environment variables to `secrets.yaml` removes a genuine attack surface. The file is explicitly required to be `0600`. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/secrets.py)

The local-backend problem remains the important exception.

# 6. Compatibility and maintainability

The current compatibility layer is substantially improved compared with an exception-driven compatibility strategy.

`register_tool` uses `inspect.signature()` to determine whether `check_fn` is supported. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/compat.py)

The configuration path has also been simplified to the native Hermes `get_config()` mechanism, consistent with the current Hermes plugin API. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/config.py)

Hermes' current middleware API confirms that `tool_execution` is the correct extension point for wrapping the actual tool invocation. [GitHub](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/developer-guide/middleware.md?utm_source=chatgpt.com)

One concern remains: the compatibility helper for hooks deliberately catches registration failures. That is fine for an ordinary observer, but **not for a security-critical redaction hook**.

In other words:

> Generic compatibility logic should not override security-specific fail-closed requirements.

# 7. Performance and reliability

The performance design is generally reasonable.

### Good

- lazy authentication avoids blocking plugin startup;
- subprocess timeout exists;
- retry counts are bounded;
- exponential backoff is capped;
- Bitwarden synchronization is interval-controlled;
- placeholder count is bounded. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/vaultwarden/auth.py)

### Potential issue

The authentication path can perform:

```text
bw status
→ login/configure
→ unlock
→ sync
```

and multiple tool calls can converge on the same `AuthManager` lock.

That is safe from a correctness perspective because the state machine is locked, but the first tool invocation can still incur several external subprocess/network operations. This should be tested under concurrent tool load.

I would classify this as **performance acceptable, but concurrency testing required** rather than a present defect.

- pytest
- pytest-mock
- ruff

The actual security-sensitive external dependency is therefore:


plus OpenSSH for SSH functionality.

One thing I would add to CI is a **real dependency/provenance test** verifying the exact expected `bw` version and checksum/digest used in production images.

# 9. Recommended remediation plan

## 1. Immediate fixes

### A. Make `post_tool_call` registration mandatory — **HIGH**

Change startup semantics to:

```text
middleware unavailable → refuse plugin
post_tool_call unavailable → refuse plugin
```

Do not allow the plugin to operate in a degraded mode where secret injection works but output redaction does not.

### B. Fix placeholder consumption — **MEDIUM**

Make this atomic:

```text
consume token
    ↓
obtain entry
    ↓
fetch secret
    ↓
create temp file
```

Do not `consume()` followed by `peek()`.

### C. Test repeated-placeholder attacks

Add tests for:

```text
$TOKEN
$TOKEN $TOKEN
"$TOKEN" "$TOKEN"
$(printf '%s' "$TOKEN") "$TOKEN"
```

and assert that the secret is injected according to the exact intended single-use semantics.

### D. Fix/remove SecretSource option

`allow_startup_secret_injection=true` must either work completely or be rejected during configuration validation.

---

## 2. Short-term improvements

### E. Fail closed on local backend

For a production security mode:

```text
terminal.backend == local
        ↓
plugin refuses to activate
```

Allow an explicit insecure-development override if necessary.

### F. Harden `.bw-data`

Apply:

- symlink rejection;
- owner verification;
- parent directory verification;
- trusted-root enforcement.

### G. Replace inherited PATH

Use a fixed minimal PATH such as:

```text
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

or, better, whatever exact runtime paths are actually required by the deployment.

---

## 3. Long-term improvements

### H. Add an adversarial security test suite

At minimum:

- repeated placeholder;
- placeholder inside shell quotes;
- placeholder inside URL;
- placeholder inside command substitution;
- secret containing `$`, `` ` ``, quotes, newlines and Unicode;
- secret echoed by terminal;
- terminal failure;
- terminal timeout;
- middleware registration failure;
- post-hook registration failure;
- concurrent tool calls;
- process termination during secret injection;
- SIGKILL stale-file recovery;
- symlinked `.bw-data`;
- replaced `bw` binary;
- malformed `bw` JSON;
- malicious/huge `bw` output;
- wrong Vaultwarden account;
- wrong server;
- expired session.

### I. Add production-image verification

Verify:

```text
bw path
bw version
bw SHA-256
OpenSSH version
plugin version
Hermes version
```

as part of deployment CI.

# 10. Final verdict

**I would not approve v0.5.2 for production yet.**

The underlying design is actually quite good for a security-sensitive Hermes plugin. The strongest pieces are the binary pinning, memory-only session handling, isolated Bitwarden profile, `0600` secret-file injection, and the decision to use `tool_execution` middleware rather than putting plaintext secrets into the command/request context. [GitHub](https://raw.githubusercontent.com/thieneret/hermes-vaultwarden-plugin/main/plugins/vaultwarden/bw_cli.py)

But the **HIGH VW-01 issue is a release blocker** because it creates an inconsistent security boundary: the plugin deliberately refuses to run without the injection middleware, yet can run without the post-execution redaction mechanism.

I would therefore rate it:

> **HIGH risk — not production-ready; approximately 1 high-severity and several medium-severity issues, with no evidence of a straightforward remote compromise of the Vaultwarden account itself.**

After fixing VW-01 and VW-02, enforcing the local-backend policy, and adding the adversarial tests above, I would expect the residual risk to fall to approximately **MEDIUM/LOW**, depending on the deployment's privilege separation.

The current repository is publicly marked as an MIT-licensed project and describes itself as security-sensitive, but also explicitly says it was AI/vibe-coded and should be audited before production use. [GitHub](https://github.com/thieneret/hermes-vaultwarden-plugin)
